## Headline

**Every point estimate in this paper reproduces exactly. Every deviation is in a randomization-inference p-value — and the archived code cannot produce those p-values reproducibly at all.** All four Table 2 treatment effects and standard errors reproduce to the printed digit (0.05/0.02 on N=1,863; 0.03/0.02 on N=1,862; 0.04/0.05 on N=458; −0.03/0.03 on N=458), as do all six Figure 3 and Figure 4 panel labels (43/45, 33/35, 32/27, 7/8, 3/0 percentage points). Two of these matter beyond the rubric arithmetic:

- **Pxp7_bj3dj5 fails, and its verdict is knife-edge.** Paper p = 0.342; reproduced 0.2879. The Criterion Guide's exact-p approximate band is [0.292, 0.392], and 0.2879 falls **0.0041 below the lower bound** → **not reproduced**. I re-ran the identical code three times and got **0.2879 every time, bit-identical** — so this is not a lucky draw. But when I varied Stata's sort tie-break seed (the setting that, as shown below, actually drives this procedure), the same unmodified code returned 0.2935, 0.2872 and 0.2902 — and **one of those four streams, 0.2935, lands inside the band and would score `approximate` instead**. The headline stays `not` because that is what the archived code returns under default settings, but the paper-level `not` rests on this single claim and on an undocumented sorting setting. Full detail in `REPLICATE_RI_RESULTS.md`.
- **Pxp7_gq9rkp changes significance.** The paper reports p = 0.086, starred `*` against its own `p < 0.10` legend. The reproduction returns **0.1152, above 0.10** — the star would disappear from Table 2 row 2, turning "weak evidence that the tax treatment caused a three percentage point increase" into a null result. The rubric still scores this `approximate` (0.1152 is within 0.05 of 0.086), but the substantive significance flip is the more important fact and is flagged here rather than left in the table.

**The cause is a bug in the archived randomization-inference code, and it is not the kind that can be patched into agreement.** `blorasim_ri_embed.ado` line 91 places `set seed 20110110` **inside** the routine that `simulate` calls 10,000 times, so the RNG is re-seeded identically at the top of every replication and the seeded draws (`rand_block`, `rand_i`) are the *same numbers* in all 10,000 reps. The results vary anyway because Stata's default `sort` breaks ties using a **separate** RNG stream that `set seed` does not reset — I confirmed this directly on a toy dataset: re-issuing `set seed` does not restore a tie order, while `set sortseed` does, reproducibly. So the entire randomization distribution is generated by an undocumented sort tie-breaking side effect rather than by the author's randomization design. Making the three sorts stable collapses the distribution to a single point (SD = 0 across 50 reps) and drives the RI p-value to exactly 0.

Two consequences, both counter-intuitive. First, the archived code is **more** reproducible than its own README claims — three independent invocations returned bit-identical p-values, because the sort stream starts from the same state in every Stata session — so the author's disclaimer that *"your results may differ slightly … because of the stochastic process"* is not what explains the gaps. Second, that reproducibility is worthless, because the number being reproduced is an artifact: changing `set sortseed`, a setting with no statistical meaning, moves the p-values by about one nominal MC SE. The gaps against the paper (up to 0.054) are roughly an order of magnitude larger than that, and the paper's values fall outside the range spanned by every tie-break stream I tried — so the paper-vs-reproduction differences are **systematic**, most plausibly an environment difference (the archived programs declare `version 11.1`; this run used Stata 16.0 MP, whose sort implementation need not agree), and the archived code offers no way to pin it down because it never controls the stream that drives its own output.

## Diagnostics — author-bug analysis

### The bug: `set seed` is inside the simulation loop, so the randomization distribution is an artifact of Stata's sort

**Suspected bug.** `blorasim_ri_embed.ado`, line 91, inside `program define blorasim_ri_embed`:

```stata
	sort block

	egen blocktag=tag(block)


	set seed 20110110

	g rand_block=uniform() if blocktag==1
	replace rand_block=rand_block[_n-1] if rand_block==.
	g rand_i=uniform()
```

`blorasim_ri_embed` is the routine that `blora_ri`'s `simulate ... ,reps(10000)` calls 10,000 times. A `set seed` placed inside it re-seeds the generator at the start of **every** replication, so `rand_block` and `rand_i` take **identical values in all 10,000 reps**. A seed belongs outside the loop (or should be omitted so `simulate` can advance the stream); placing it inside is the textbook way to destroy a simulation's variation.

**Reasoning.** If the seeded draws are identical every rep, the re-randomized assignment `z` should also be identical every rep, and the RI p-value should degenerate to 0 or 1. It does not — the observed distributions are well spread. The explanation is that the assignment does not depend only on the *values* of `rand_i` but on the **row order** they land in: `sort block` (line 86) has massive ties, and Stata's default `sort` breaks ties using a separate RNG stream that `set seed` does **not** reset. Different tie-breaking permutes which row receives which `rand_i` value, which changes `sort vill_code sex_Z rand_block rand_i`, which changes `count`, which changes `z`. So all the apparent randomness comes from Stata's sort tie-breaking, not from the author's randomization design.

**Demonstration (`diagnostic_seed.do` / `diagnostic_seed.log`).** I ran the archived routine for 50 replications, then re-ran a copy in which the only change is `sort block` → `sort block, stable`, `sort vill_code sex_Z rand_block rand_i` → `, stable`, and `bysort block3:` → `sort block3, stable` + `by block3:` (`diagnostic_seed_stablesort.ado`; `diff` against the original shows exactly those three lines). Result:

```
AS-ARCHIVED (default sort):
    Variable |        Obs        Mean    Std. Dev.       Min        Max
       b_y_2 |         50   -.0034007    .0229388  -.0597666   .0442435
       b_y_5 |         50   -.0011697    .0189396  -.0615199   .0366339

STABLE SORT (seed now fully controls the draw):
       b_y_2 |         50    .0019312           0   .0019312   .0019312
       b_y_5 |         50   -.0169462           0  -.0169462  -.0169462
RI p-value for the tax ATE under stable sorting = 0
```

With stable sorting the "randomization distribution" collapses to a **single point** (SD exactly 0) and the RI p-value degenerates to **exactly 0**. That is conclusive: the seed placement, not the design, is what determines whether this code produces a distribution at all.

**Patched run.** *There is no patch that recovers the paper's numbers, and I did not promote one.* The two candidate fixes both fail as reconciliations:
1. **Move `set seed` outside the loop** — then every rep draws fresh, the distribution is genuine, and the p-values are simply a fresh random sample; that is what my headline runs already approximate (since the in-loop seed is inert), so it changes nothing.
2. **Make sorting deterministic** — as shown, this collapses the distribution and produces degenerate p-values of 0 or 1, which contradicts every value printed in Table 2.

This is why the report carries no "verdict if patched": the defect makes the published p-values **unrecoverable**, not merely misplaced. The author's archive anticipates this in part — `Do_Blora_Analysis.do` warns *"Your results may differ slightly from what is reported in the text because of the stochastic process. The original randomization inference results are available from the author upon request"* — but "slightly" is not the right characterisation when the p-value for gq9rkp moves across the paper's own significance threshold and the one for bj3dj5 moves out of the reproducibility band.

**Confidence: high** that this is a genuine code defect (the stable-sort demonstration is decisive and the line placement is unambiguous). **Medium** that it is the *sole* explanation for the size of the five p-value gaps — the author states that the archived code is the same code that produced the published p-values, so an additional Stata-version difference in sort tie-breaking behaviour between the author's Stata (version 11.1 is declared in the programs) and Stata 16 here is plausible and would compound the effect. I cannot test that without the author's Stata version.

### Replicate runs — how much does the p-value actually move between identical runs?

Because the `not` verdict on **bj3dj5** sits only 0.0041 (0.9 nominal MC SEs) outside the approximate band, the headline verdict for the whole paper turns on whether that gap is stable. I ran two experiments; both are written up in full in **`REPLICATE_RI_RESULTS.md`**.

**Experiment 1 — repeat the identical run.** Four extra 10,000-replication runs of the unmodified `blora_ri`, each a separate Stata invocation with default settings. **Every one is bit-identical to the primary run:**

| Outcome | Statistic | Primary | Replicate 2 | Replicate 3 |
|---|---|---|---|---|
| `votefor_3` | pv_5_tt | 0.2879 | 0.2879 | 0.2879 |
| `q146_learnmore_govt_REC2` | pv_5_tt | 0.1152 | 0.1152 | — |
| `q147_learnmore_apbd_REC2` | pv_2_tt / pv_5_tt | 0.0121 / 0.0058 | 0.0121 / 0.0058 | — |

**Experiment 2 — vary the sort tie-break stream.** `diagnostic_sortrng.do` first confirms the mechanism on a toy dataset: re-issuing `set seed 20110110` does **not** restore a tie order (RUN A `16,12,20,8,4,…` vs RUN B `8,12,20,4,16,…`), while `set sortseed 999` does, exactly (RUN C = RUN D). Re-running the unmodified RI with three arbitrary sort seeds:

| `votefor_3`, pv_5_tt | default (×3) | sortseed 11111 | sortseed 22222 | sortseed 33333 |
|---|---|---|---|---|
| Reproduced RI p | 0.2879 | **0.2935** | 0.2872 | 0.2902 |
| vs band lower bound 0.292 | below | **above** | below | below |
| Sub-verdict | not | **approximate** | not | not |

Mean 0.28970, SD 0.00284, range 0.2872–0.2935. **One of the four tie-break streams flips bj3dj5 from `not` to `approximate`** — the classification is decided by an undocumented Stata sorting setting rather than by anything statistical. The headline retains `not` because that is what the archived code produces under default settings, but the fragility is material and is why it is stated here and in the Headline.

For `q146_learnmore_govt_REC2` the p-value moved from 0.1152 to 0.1082; both exceed 0.10, so the **significance flip on gq9rkp is robust** to this variation.

Finally, note the scale mismatch: tie-break variation moves these p-values by roughly ±0.006, whereas the gaps against the paper run to 0.054, and the paper's values lie outside the range spanned by every stream tested. The reproduction's disagreement with the paper is therefore systematic, not an accident of tie-breaking.

### Nothing else to diagnose

Every point estimate — four Table 2 treatment effects, four Table 2 standard errors, four sample sizes, and all ten Figure 3/4 panel labels — reproduces the published value exactly from unmodified code. No bug is suspected in the analysis of the deterministic quantities, in the data, or in the `blora_tax_ate` / `blora_tax_cate` routines.
