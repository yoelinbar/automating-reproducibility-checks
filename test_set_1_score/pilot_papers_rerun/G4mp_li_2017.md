## Headline

The archived Stata code, run unmodified on the archived data, reproduces the published result exactly: the coefficient on "may create 1,000 local jobs" is **0.2454** (robust SE clustered on respondent = 0.0414, t = 5.93, 95% CI [0.164, 0.327], N = 8,240), which rounds to **0.25** at the paper's printed precision — identical to the value printed on p. 202. **The one deviation in this paper is not in the reproduction but in the upstream extraction:** `claims_for_verification_clean.csv` records `orig_coef_value = 0.24` and `orig_effect_size_value_repro = 0.24`, whereas the published version of record prints **0.25** in text (and the CSV's own `claim_result_text` also says "approximately 0.25"). The extracted 0.24 appears to be either a truncation of 0.2454 or a read-off from the Figure 1 coefficient plot; it is not what the paper prints. Per the plan's rounding rule, the comparison target is the paper's text value (0.25), and against it the reproduction is precise. Had the audit anchored on the extracted 0.24 instead, the same reproduced number would have been graded *approximate* (2.2% off) — the extraction error is verdict-relevant and is flagged here as such.

## What I did

**1. Set-up.** Created `independent_reproductions/G4mp_li_2017/`, copied `papers/G4mp.pdf` in, and ran `pdftotext -layout G4mp.pdf G4mp.txt`.

**2. Extraction check.**
- Focal coefficient — p. 202, RESULTS section, in text: *"The coefficients on the 'impact on local job market' variable show that support for a project increases by **0.25** points if it could create local jobs and decreases by 0.42 points if the project may lead to job losses."* The paper reports this coefficient **only in text and in the Figure 1 coefficient plot**; there is no regression table in the article. Per the plan's rule ("When both text and figure carry the value, use the text"), the original value is **0.25**, printed to 2 decimals.
- **Extraction mismatch (flagged):** CSV `orig_coef_value` = 0.24 and `orig_effect_size_value_repro` = 0.24 ≠ paper's 0.25. Note the CSV's own `claim_result_text` field reads "approximately 0.25", i.e. the numeric extraction contradicts the claim text it accompanies. I did not use graphreader on Figure 1 to manufacture a finer-precision target — the plan explicitly identifies that as the incorrect path.
- Sample size — Fig. 1 note, p. 201: *"(N = 8,240)"*; and p. 200: *"Our design yields a total of 8,240 (1,030 × 2 × 4) FDI projects."* CSV `orig_sample_size_value` = 8240 ✓ matches.
- No p-value, SE, or test statistic is printed for this coefficient anywhere in the article; CSV correctly records these as NA.

## Diagnostics — author-bug analysis

**Diagnostics: none** — the unpatched run reproduces the published value; no logic bug suspected in the posted code or data. Nothing was patched, and no "verdict if patched" applies.

One observation about the archive that is *not* a bug: `code.do`'s summary-statistics lines use positional row filters (`if college==0 & (_n<2225 | _n>22146)`, `if _n<2225`, `if wave == 2 & _n<18415`), which are fragile to any re-sort of the dataset. They affect only the descriptive Tables 1/C2/C3, not the focal regression, and they ran without error on the archived data as sorted. The focal model uses only the substantive filter `college==0` and is unaffected.

The only defect uncovered in this paper's audit chain is upstream of the paper: the **extraction records 0.24 where the published paper prints 0.25**. That is an extraction error, not an author error, and it is reported in the Headline and Comparison table rather than here.
